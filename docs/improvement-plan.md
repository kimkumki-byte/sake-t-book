## A. 새 요청 2가지

### A-1. 리뷰를 고쳐도 처음 쓴 날짜가 보이게

**지금 왜 이렇게 되나**
- 평가 표(`ratings`)에는 "처음 쓴 시각" 칸이 없고, `updated_at`(마지막으로 고친 시각) 하나만 있어요.
- 저장할 때마다 `updated_at`을 지금 시각으로 덮어써요 (`lib/store.js` upsertRating).
- 리뷰 목록·MY·CSV·홈 친구 소식이 모두 이 `updated_at`을 날짜로 보여줘요.
  → 그래서 고치면 날짜가 바뀌고, 홈 친구 소식에도 "방금 평가했어요"로 다시 올라가요.

**고치는 방법**
1. DB: `ratings`에 `created_at`(처음 쓴 시각) 칸 추가. 고칠 때는 이 칸을 건드리지 않음.
2. 화면에 보이는 날짜는 `created_at`. "(수정됨)" 표시는 하지 않기로 함 (2026-11-26 사용자 결정).
3. 홈 친구 소식도 `created_at` 기준 → 고치기만 해선 소식에 다시 안 뜸.

**⚠️ 이미 있는 리뷰의 원래 날짜**
- 이미 고쳐진 리뷰는 원래 날짜가 DB에 남아 있지 않아 되살릴 수 없어요.
- 새 칸을 처음 채울 때 지금의 `updated_at` 값으로 채워요 (가장 그럴듯한 값). 이후로는 정확해요.

### A-2. 같은 사케에 리뷰를 여러 번 남기기

**지금 구조**: "한 사람 + 한 사케 = 평가 1개" 규칙이 DB(`unique (sake_id, nickname)`)와 서버(upsert)에 박혀 있어요.
이 규칙을 풀면 영향이 꽤 넓어서, 아래처럼 바꿔야 해요.

| 영역 | 바꿀 내용 |
|---|---|
| DB | 유일 규칙 삭제, `created_at` 추가, 인덱스 정리. `update-7-multi-reviews.sql` + `schema.sql` |
| 서버 `rate` | "새 리뷰 추가"(POST)와 "이 리뷰 수정"(PATCH, 리뷰 번호로) 분리, 내 리뷰만 고칠 수 있게 검사. **리뷰 삭제**(DELETE) 추가 |
| 서버 `sake` 상세 | 내 리뷰가 여러 개 → 목록으로. "나 포함 N명"은 **사람 수**로 |
| 평균·랭킹 | 한 사람이 5번 쓰면 평균이 그 사람 쪽으로 쏠림 → 사람당 1표로 계산 (아래 결정 1) |
| 레벨·뱃지 | 리뷰 수로 셀지, 마신 사케 수로 셀지 (결정 2). "양조장 5곳" 같은 뱃지는 중복 없이 셈 |
| 개척자 뱃지 | 그 사케 첫 리뷰를 쓴 사람 → 지금 계산 그대로 됨 |
| 비슷한 친구 | 사케별 그 사람의 대표 별점(결정 1과 같은 기준)으로 비교 |
| 사케 목록·오술 | "평가 완료" 칩: 리뷰가 하나라도 있으면 완료, 날짜·별점은 가장 최근 것. "2회" 표시 |
| 캘린더 | 마신 날짜마다 따로 찍힘 (같은 사케가 여러 날에 나옴) |
| MY | 내 리뷰 목록에 모두 나옴, 각각 수정·삭제. 올해 리포트·CSV도 리뷰 단위 |
| 화면 | 상세: "내 기록" 목록 + "다시 마셨어요(새 리뷰)" 버튼. 평가 화면: 새로 쓰기 / 수정 구분 |
| 데모·테스트 | `preview/mock-api.js`, `tests/fake-store.js`, `tests/run.js` 모두 같은 규칙으로 |

**블라인드 규칙은 그대로**: 리뷰가 하나라도 있으면 평균·남의 리뷰가 열려요.

## C. 점검 결과 (구조·완성도)

중요도: 🔴 꼭 고치기 · 🟠 고치면 좋음 · 🟢 여유 있을 때

### 🔴 1. 평가가 1000개를 넘으면 계산이 조용히 틀려짐
- Supabase(PostgREST)는 한 번에 최대 **1000줄**만 돌려주는 게 기본값이에요.
- 홈·랭킹·MY·레벨 계산이 "모든 평가"를 한 번에 가져오는데(`allRatings`), 1000개를 넘으면 나머지가 **오류 없이 빠져요**.
  → 랭킹·레벨·뱃지가 틀어짐. 여러 번 리뷰가 되면 더 빨리 1000개에 닿아요.
- 해결: 1000개씩 나눠 받기(페이지 넘김), 또는 계산을 DB 함수로 옮기기. **A-2와 같이 하는 걸 추천.**

### 🔴 2. 로그인 비밀번호 무한 시도 가능
- 틀리면 0.4초 기다리게만 하고 횟수 제한이 없어요. 비밀번호는 4자부터라 짧아요.
- 해결: 닉네임별로 "5번 틀리면 10분 잠금"(DB에 실패 횟수 기록). 무료로 가능.

### 🔴 3. README에 실제 비밀 키 예시가 적혀 있음 (CLAUDE.md 8장에도 메모)
- 그 값을 실제로 쓰고 있다면 누구나 로그인 쿠키를 위조할 수 있어요(저장소가 Private이라 위험은 낮음).
- 해결: Vercel에서 `SESSION_SECRET`을 새 긴 값으로 바꾸고(사용자 직접), README의 값은 지움.

### 🟠 4. 운영자 닉네임을 바꾸면 운영자의 리뷰가 떨어져 나감
- 운영자 닉네임은 환경변수(`ADMIN_NICK`)에서 오고, 평가는 닉네임 글자로 연결돼요.
- 해결: 당장은 "운영자 닉네임은 바꾸지 않기"를 CLAUDE.md에 적어 두기. 길게는 회원 번호로 연결(아래 7번).

### 🟠 5. 화면 파일 하나가 1,478줄
- `public/app.js` 한 파일에 모든 화면이 있어 고칠 때 실수 위험이 커요.
- 해결: 빌드 도구 없이 파일만 나누기(공통 도우미 / 화면별 / 이벤트). 동작은 그대로, 테스트로 확인.

### 🟠 6. 보안 헤더 보강
- `vercel.json`에 CSP(허용된 곳의 스크립트만 실행) 헤더가 없어요. 화면은 글자를 잘 이스케이프하고 있어서 지금 문제는 없지만, 한 겹 더 막는 장치예요.

### 🟢 7. 평가·찜이 회원 번호가 아니라 닉네임으로 연결됨
- 닉네임 변경 함수로 잘 처리하고 있어 지금은 문제 없음. 회원이 많아지면 번호로 바꾸는 게 안전. (큰 작업이라 나중에)

### 🟢 8. 사진 정리
- 사케 등록 중 실패하면 올린 사진이 보관함에 남을 수 있어요. 무료 용량(1GB)이라 당장은 괜찮음.

### 🟢 9. 이 폴더가 아직 git에 연결되지 않음
- 배포 전에 CLAUDE.md 3장의 "처음 한 번" 순서로 연결해야 해요.

### 잘 되어 있는 점 (그대로 두기)
- 블라인드 규칙을 화면이 아니라 **서버에서** 지킴
- 모든 표 RLS 잠금 + 서버 비밀 키만 접근, DB 함수 권한 정리
- CSRF 헤더 검사, HttpOnly 쿠키, 비밀번호 bcrypt
- 서버·데모가 같은 계산 파일(`lib/core.js`)을 씀 → 데모가 실제와 같음
- 함수 1개로 합친 속도 구조, 캐시·미리 받기
